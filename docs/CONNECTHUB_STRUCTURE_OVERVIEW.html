1. Project Purpose

ConnectHub is a real-time communication platform designed for more than normal chat. It supports user onboarding, room-based communication, live message delivery, presence, notifications, multilingual translation, and payment-based credit top-up in one connected system.

Business Goal

  • enable fast communication between users and teams
  • remove language barriers with message translation
  • support premium translation credits with payment integration

Technical Goal

  • split responsibilities into focused services
  • support real-time delivery and scalable communication
  • make the platform easier to maintain and extend

2. How the System Is Structured

The system follows a microservices model. Each service owns a specific responsibility, while the API Gateway, Eureka, Kafka, Redis, and databases support communication and reliability.

Client Layer Web or mobile frontend sends HTTP requests and WebSocket events.
Gateway Service Single public entry point for routing requests to internal services.
Eureka Server Service registry used so services can discover each other dynamically.
ConnectHub Core Platform
Real-Time + Event-Driven + Service Based
Kafka Handles asynchronous chat and credit top-up events.
Redis Stores fast-changing user presence data.
Databases Store users, rooms, messages, notifications, and payments.

3. Service Responsibilities

Service Main Responsibility Why It Exists
Gateway Service routes all client requests keeps one public entry point and hides internal complexity
Auth Service registration, login, profile, contacts, credits acts as the identity and user account center of the platform
Room Service rooms, members, admins, room metadata controls who can communicate with whom
Message Service message persistence, history, search, attachments, reactions stores the actual conversation history reliably
WebSocket Service live delivery, typing indicators, read receipts, fan-out powers the real-time user experience
Notification Service unread notifications and read status preserves alerts even when a user is offline
Presence Service online/offline tracking handles highly dynamic status updates efficiently through Redis
Translation Service message translation separates language processing from core messaging logic
Payment Service order creation, payment verification, credit top-up connects technical features to business monetization

4. Main Functional Flows

4.1 User Onboarding Flow

Step 1 User registers through the gateway.
Step 2 Auth Service validates details and completes OTP-based registration.
Step 3 User logs in and receives account information.
Result User becomes ready for rooms, chat, and translation usage.

4.2 Room and Collaboration Flow

Step 1 User creates a group room or direct room.
Step 2 Room Service stores room details and member list.
Step 3 Admin can add, remove, or promote members.
Result The room becomes the communication boundary for chat events.

4.3 Real-Time Messaging Flow

Step 1 User sends a message over WebSocket.
Step 2 WebSocket Service forwards the event to Kafka.
Step 3 Message Service stores the message and republishes the saved event.
Result WebSocket Service broadcasts the final saved message to room users.
This is one of the strongest architectural points of ConnectHub: message acceptance, persistence, and delivery are separated into different stages, which improves reliability and scalability.

4.4 Translation Flow

Step 1 User requests translation for a message.
Step 2 Message Service consumes one translation credit from Auth Service.
Step 3 Translation Service translates the content into the target language.
Result User receives translated content and updated credit balance.

4.5 Payment to Credit Flow

Step 1 User selects a top-up plan and creates an order.
Step 2 Payment Service verifies provider payment details.
Step 3 Payment Service publishes a credit top-up event to Kafka.
Result Auth Service updates the user credit balance.

5. Supporting Platform Components

Kafka

Used for asynchronous communication where direct coupling is not ideal.

  • chat ingestion and broadcast
  • credit top-up synchronization
  • presence event publishing

Redis

Used for lightweight and fast-changing online/offline user status.

  • quick read and write for presence
  • better fit than a relational database for temporary state

Databases

Each domain keeps its own data ownership boundary.

  • users in auth database
  • rooms and memberships in room database
  • messages and attachments in message database
  • payments in payment database

WebSocket + STOMP

Provides live communication for chat-based features.

  • message delivery
  • typing indication
  • read receipts
  • live user notifications

6. Why This Architecture Is Valuable

Scalability

Services can grow independently based on load. For example, WebSocket and Message services can scale differently from Payment Service.

Maintainability

Each service owns one business domain, which makes debugging, enhancement, and onboarding easier.

Reliability

Kafka reduces tight coupling and allows the platform to process important events without blocking user actions.

Business Readiness

Translation credits and payment top-up add a monetization path instead of keeping the project as only a technical demo.

7. Best Way to Explain the Project

Recommended explanation order for managers, clients, or reviewers:

  1. start with the business problem: chat + translation + real-time collaboration
  2. show the architecture: gateway, services, Kafka, Redis, databases
  3. explain service responsibilities clearly one by one
  4. walk through the real-time message flow from client to delivery
  5. show how translation and payment create product value
  6. end with why microservices were chosen and what makes the system scalable
Best one-line explanation: ConnectHub is a microservices-based real-time communication platform that combines chat, live delivery, multilingual translation, notifications, presence tracking, and payment-driven credits in one scalable backend ecosystem.
Important presentation note: when explaining this project to a manager or client, focus first on user value and flow, then explain the technical design that enables that value. This project becomes much easier to understand when presented from outcome to architecture, not the other way around.

8. Conclusion

ConnectHub is not just a CRUD project. It is a structured communication platform where each service supports a clear business function. The architecture demonstrates distributed-system thinking, real-time communication design, asynchronous event handling, and product-oriented features such as translation credits and payment integration.
